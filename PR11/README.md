# РЗШІ — матеріали до практичних робіт

Розробка застосунків зі штучним інтелектом, 7 семестр. Мова — Python.

Це **матеріали до практичних робіт**: підготовка середовища, каркас застосунку, зразки даних і чеклісти самоперевірки. Кожній роботі відповідає своя папка; матеріали видаються архівом перед відповідним заняттям.

Папки наступних робіт додаватимуться перед відповідним заняттям.

Кожна папка влаштована однаково:

```
prN/
├─ README.md          що це за робота, з чого почати, чекліст самоперевірки
├─ requirements.txt   залежності саме цієї роботи
├─ check_env.py       перевірка середовища перед початком
└─ app/               каркас застосунку: структура є, реалізації немає
```

Решта підпапок залежить від теми: у ПР1 це `samples/` зі збереженими відповідями API, у ПР2 — `eval/` для власного набору зображень з відомим вмістом, у ПР3 і ПР4 — `compare/` для порівняння конфігурацій моделі, у ПР5 — `docs/` з колекцією документів і `compare/` для порівняння способів пошуку, у ПР6 — та сама `docs/` і `eval/` для перевірки помічника на наборі питань, у ПР7 — `samples/` із зображеннями рахунків і правильними значеннями, `reference/` з довідниками й `eval/` для порівняння якісних і погіршених зразків, у ПР8 — `shop/` з готовим сервісом магазину, до якого підключаються інструменти, і `eval/` з набором питань, у ПР9 — той самий `shop/` і `eval/` з набором звернень для порівняння workflow й агента, у ПР10 — `samples/` зі зверненнями й установленими фактами та `eval/` із сценаріями стійкости, у ПР11 — ті самі `samples/`, `eval/` зі скриптом прогону замовлень і заготовкою аналізу журналу, а `logs/` і `state/` зʼявляються під час роботи й до репозиторію не потрапляють.

## Що тут є, а чого немає

У папці роботи ви знайдете **каркас застосунку**: структуру проєкту, налаштований веб-рівень і сторінку. Це плумбінг — те, що не є предметом навчання й лише забирало б час на початку заняття.

**Розв'язків тут немає.** Функції, у яких і полягає робота, лишені заготовками з поясненням, що вони мають робити. Практичні роботи курсу не є покроковими інструкціями: у кожній сформульовано задачу й перелічено те, що ви маєте продумати самі — як структурувати запит, як повестися при збої, що модуль віддає назовні. Ці рішення за вас не ухвалює ніхто.

Крім каркаса, у папці лежать реальні відповіді зовнішніх сервісів і перелік того, що перевірятиметься на здаванні.

## Підготовка середовища

Потрібен **Python 3.10 або новіший**. Перевірити версію:

```bash
python --version
```

Для кожної роботи створюйте окреме віртуальне середовище в її папці. Windows, PowerShell:

```bash
cd pr1
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

macOS або Linux:

```bash
cd pr1
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Після встановлення запустіть перевірку середовища — вона підкаже, чого бракує:

```bash
python check_env.py
```

Якщо PowerShell не дозволяє активувати середовище (`running scripts is disabled on this system`), дозвольте скрипти для свого користувача одноразово:

```bash
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

## Ваш репозиторій

Матеріали ви отримуєте **архівом** перед кожним заняттям. Саму роботу ведіть у **власному git-репозиторії** — заведіть один на весь курс і складайте роботи в нього папками:

```
rzshi/                  ← ваш репозиторій
├─ README.md            цей файл
├─ .gitignore
├─ pr1/                 ← розпакований архів до ПР1
│  ├─ README.md         опис роботи, з чого почати, чекліст
│  ├─ requirements.txt
│  ├─ check_env.py
│  ├─ app/              каркас застосунку — тут ви пишете
│  └─ samples/
└─ pr2/                 ← розпакований архів до ПР2
   └─ …
```

1. **Створіть репозиторій** — на GitHub, GitLab або лише локально (`git init`). Робити його публічним не обовʼязково.
2. **Розпакуйте архів у корінь** репозиторію: усередині вже є папка `prN/` разом із `README.md` і `.gitignore`.
3. **Свій код пишіть у папці роботи**, поруч із її матеріалами — каркас саме для цього й лишено незаповненим.
4. **Комітьте частинами**, а не одним фінальним комітом: історія показує, як ви рухалися до рішення, і це видно на здаванні.
5. Віртуальне середовище, кеш і локальні налаштування у версіювання не потрапляють — про це подбає `.gitignore` з архіву.

Окреме віртуальне середовище створюйте **в папці кожної роботи**: набори залежностей у них різні, і спільне середовище рано чи пізно дасть конфлікт версій.

## Як здається робота

Роботу здають на занятті: ви показуєте застосунок у дії та **пояснюєте свої рішення**. Оцінюється не лише працездатність коду, а й розуміння того, чому він побудований саме так.

Перед здаванням пройдіть чекліст самоперевірки в README відповідної роботи — він повторює критерії приймання з тексту практичної.

Використовувати AI-асистента під час виконання **можна**. Здати код, який ви не можете пояснити, — ні.
